# Repository Guidelines

## Project Structure

This is a TypeScript Discord.js v14 bot. Slash commands live in `commands/`; Discord event handlers in `events/`; loading and dispatch in `handlers/`; client and response helpers in `core/`; shared business logic in `utils/`; and shared contracts in `types/`. Tests are in `test/`, images in `assets/`, maintenance scripts in `scripts/`, and operator documentation in `docs/`. Runtime SQLite and JSON data are stored in `data/`; `dist/` is generated by the build. Keep persistence and schema changes in `utils/db.ts` compatible with existing SQLite data.

## Build, Test, and Development

Use Node.js 22 or newer (`better-sqlite3` requires it) and install dependencies with `npm ci`.

- `npm run build` cleans `dist/`, compiles TypeScript, and runs the configured strict typecheck.
- `npm test` builds the project and runs the compiled tests with Node's test runner.
- `npm start` builds and starts the bot.
- `npm run register` publishes the current slash-command schemas to Discord; run it after changing command definitions.
- `npm run security:check` builds and runs the repository security scan.

## Coding and Testing Conventions

Match nearby TypeScript: two-space indentation, double quotes, and semicolons. Keep command modules named in lowercase (for example, `commands/ping.ts`) and tests as `*.test.ts` under `test/`. Use the existing command types and shared helpers rather than duplicating interaction or database logic. Add focused `node:test` cases with `node:assert/strict` for behavior changes. `npm run typecheck:strict` currently checks the modules listed in `tsconfig.strict.json`; run `npm test` for the full build and test pass. No formatter or linter script is configured in `package.json`, so follow the surrounding style.

## Commits and Pull Requests

Recent commits use short Conventional Commit-style prefixes such as `feat:`, `fix:`, `test:`, and `docs:`; keep the subject concise and action-oriented. A pull request should explain the user-visible change, list validation performed, and call out configuration or data changes. Include screenshots only when a change affects a visual Discord response or other UI.

## Configuration and Data Safety

Keep Discord tokens and other secrets in local environment configuration; never commit them. Treat `data/` as persistent user state: do not delete or reset it during development, and preserve backward compatibility when changing schemas.
